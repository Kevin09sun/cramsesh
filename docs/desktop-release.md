# Desktop builds and releases

This is a maintainer reference. For installation and normal use, start with [Getting started](getting-started.md).

## Platforms and prerequisites

| Platform | Release runner | Packages | In-app update |
| --- | --- | --- | --- |
| Windows, x64 | `windows-2025` | Unsigned per-user NSIS installer | NSIS |
| Linux, x64 | `ubuntu-24.04` | AppImage + `.deb` | AppImage replacement; `.deb` through dpkg/apt, with elevation if needed |
| macOS, Apple Silicon | local only | Unsigned local DMG + ZIP | not shipped |

1.0.0 ships Windows and Linux. The macOS packaging configuration stays in [`electron-builder.yml`](../electron-builder.yml) for local unsigned builds, but the release matrix's Mac entry is disabled until the owner has an Apple signing account. There is no macOS release job, no notarization, and no `latest-mac.yml` in 1.0.0.

Windows may show SmartScreen/unknown-publisher warnings because the installer is unsigned. AppImage is the primary Linux download; `.deb` updates may require an administrator password. Both use the same download/restart banner. Targets/signing are defined in [`electron-builder.yml`](../electron-builder.yml); CI/release uses **Node 26**.

Windows/Linux use flat-design icons generated by `scripts/make-icons.mjs`. Linux desktop identity is `cramsesh.desktop`. The custom app bar remains on both platforms: right-side native Window Controls Overlay, with the native menu revealed by Alt.

## Build pipeline

Build **on each target OS**. Next traces native binaries for its build machine; a macOS standalone tree is not a Windows/Linux payload.

1. `npm ci`
2. Run native renderer/browser-service tests in Electron's Node:
   ```sh
   ELECTRON_RUN_AS_NODE=1 NODE_ENV=test npx electron --import tsx --test tests/pdf-native-render.test.ts tests/pdf-ops.test.ts tests/svg-native-render.test.ts tests/browser-service.test.ts
   ```
   This environment-prefix syntax is for a POSIX shell; CI uses Bash on every OS.
3. `npm run build`
4. `node scripts/smoke-provider-runtime.mjs` — check the **fresh trace before curation**, including native provider initialization and fixture payloads, not real sign-in/generation.
5. `node scripts/build-server.mjs` — copy static assets, validate prompt assets, refuse known data/credential leaks, and remove only standalone-root old installers/development Electron.
6. `node scripts/smoke-server.mjs --electron` — check renderer/demo dependencies, providers, gzip backpressure, and isolated standalone HTTP boot under Electron's Node.
7. Package with Electron Builder using the appropriate local/release policy below.

The shell/updater ships in `app.asar`; the server/native renderers ship unpacked as `extraResources`. Pi/PDF/canvas/resvg/Photon dynamic assets are explicitly traced in [`next.config.ts`](../next.config.ts). Keep trace exclusions narrow: broad `dist/**` or `data/**` patterns can remove dependency assets. Curation guards are not a substitute for inspecting a changed payload.

The release workflow also checks providers from the **packaged** payload under host Node and packaged Electron, then exercises the demo helper using the app's Electron (Xvfb on Linux). HTTP boot or catalog output alone does not test these lazy paths.

`smoke-image-runtime.mjs` separately checks synthetic Photon in-process/worker resizing in standalone output. It accepts `--standalone <dir>` and `--runtime <binary>`; it is **not currently invoked by CI/release workflows**.

### Local packages

`npm run desktop:dist` is the local **unsigned macOS** path for developers on a Mac; it is not how 1.0.0's Windows or Linux releases are built. It clears `dist` and `.next/standalone`, builds, checks the fresh provider trace, curates, runs the server smoke under **host Node**, and packages a locally unsigned Mac app with notarization off.

For Windows/Linux, perform steps 1–6 on that OS, then:

```sh
npx electron-builder --win --x64 --publish never    # Windows
npx electron-builder --linux --x64 --publish never # Linux
```

## CI and release modes

[CI](../.github/workflows/ci.yml) runs typecheck/tests/lint on Ubuntu, plus standalone/native checks on macOS, Windows, and Linux.

[Desktop release](../.github/workflows/release.yml) has two modes:

- **Manual dispatch:** unsigned rehearsal installers for Windows and Linux, retained as workflow artifacts for seven days. No release creation or publication, and no signing secrets.
- **Matching `v<package.json version>` tag:** gates, one shared draft-preparation job, Windows and Linux packaging/upload jobs, then read-only draft verification. Published/ambiguous existing releases fail preparation; same-ref runs serialize rather than cancelling uploads. **The workflow never publishes the draft.**

### Draft verification

[`scripts/verify-release.ts`](../scripts/verify-release.ts) runs after both packaging jobs. It requires one draft matched by `v<version>` or bare `<version>`, refusing zero/two matches or a published match. Bare-version matches warn because later runs could split assets across tags.

The draft must contain **exactly 6 uploaded, nonempty assets**:

| Assets | Purpose |
| --- | --- |
| `Cramsesh-<v>-x64-setup.exe` + `.blockmap` | Windows installer/updater |
| `Cramsesh-<v>-x86_64.AppImage` | Linux AppImage |
| `Cramsesh-<v>-amd64.deb` | Debian package |
| `latest.yml`, `latest-linux.yml` | Updater feeds |

Feed versions, exact referenced asset sets, bare filenames, and sizes must agree; missing/stale extra assets, path traversal/URLs, or builder naming drift fail validation. The validator does not download/hash every installer; it checks draft metadata and downloaded feeds.

The verification job needs `contents: write` to list private drafts but performs GET-only operations. Its token is exposed only to release listing/feed download, not dependency installation or offline validation.

### Signing secrets

1.0.0 uses **no code-signing or notarization secrets**. The Windows installer is unsigned and Linux packages are unsigned. The built-in `GITHUB_TOKEN` supplies the scoped `GH_TOKEN` used to upload draft assets; no separate release token is needed. Never commit keys, certificates, passwords, or environment-secret files.

## Release runbook

1. Agree scope/version and complete relevant gates and human functional acceptance. Use manual dispatch if rehearsal installers are useful.
2. Update package/lockfile versions, check the intended source on main, and push the authorized matching tag.
3. Wait for **both OS jobs and Verify draft release**. Inspect the single draft's tag, notes, 6 assets, and feeds. Diagnose failures before retrying. Re-upload replaces same-named assets; stale extras still fail. Deleting assets/releases is a mutation, not verification.
4. If editing draft metadata, include canonical **`tag_name: "v<version>"` in every metadata PATCH**, even for title/body changes; omission has reset tags before. Re-read tag, draft status, and assets afterward. A tag correction does not authorize deleting/recreating a release.
5. The owner checks the packaged build as needed and explicitly publishes the complete draft. Confirm public installers and feeds; use a prior installed version for real update-path checks.

Shell, native-module, packaging/updater, or Electron changes warrant focused platform checks: install/open, window controls/dragging/zoom, setup/resume, PDF/SVG, and demo helper. Fixture gates do not prove account functionality or lesson quality. Do not repeat accepted feature testing without a concrete risk.

## Updates

Packaged apps check at startup and every 24 hours by default, download automatically, and install on quit or Restart. **Settings → General** provides release notes, manual checks, status, and Automatic updates. Disabling automatic checks does not cancel downloads/staged installs; manual checks still download updates. Dev builds disable the updater. Errors go to `userData/logs/main.log`; `LH_UPDATE_FEED` is a test-only generic-feed override.
